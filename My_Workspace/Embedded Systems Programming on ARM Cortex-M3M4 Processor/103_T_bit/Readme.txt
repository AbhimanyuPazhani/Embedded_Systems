
ARM Cortex-M Privilege Levels and Processor Modes Demonstration

Description
This project demonstrates key ARM Cortex-M processor concepts using a
simple STM32 application:

- Thread mode vs Handler mode
- Privileged vs Unprivileged access level
- CONTROL register manipulation
- Software-triggered interrupt using STIR
- Exception entry and ISR execution
- ARM Thumb (T-bit) behavior on Cortex-M processors

The code is written to align with the concepts taught in the
Embedded Systems Programming on ARM Cortex-M3/M4 course by
FastBit Academy.


Target Environment

- MCU Architecture: ARM Cortex-M3 / Cortex-M4
- IDE: STM32CubeIDE
- Toolchain: arm-none-eabi-gcc
- Execution Model: Bare-metal (no RTOS)


Program Flow Overview

1. Thread Mode (Privileged)
After reset, the processor starts execution in:
- Thread mode
- Privileged access level

The `main()` function executes in this context.


int main(void)
{
    printf("In thread mode : before interrupt\n");
    change_access_level_unpriv();
    generate_interrupt();
    printf("In thread mode : after interrupt\n");
}

2. Switching to Unprivileged Thread Mode

The function `change_access_level_unpriv()` modifies the **CONTROL register**
to set the `nPRIV` bit.


__asm volatile ("MRS R0, CONTROL");
__asm volatile ("ORR R0, R0, #0x01");
__asm volatile ("MSR CONTROL, R0");


This causes:

* Thread mode → Unprivileged
* Handler mode remains Privileged (unchanged)

Once unprivileged, the code **cannot revert back** without an exception.



3. Software-Generated Interrupt (STIR)

The function `generate_interrupt()` performs two actions:

1. Enables IRQ3 using NVIC ISER
2. Triggers IRQ3 using the **Software Trigger Interrupt Register (STIR)**


*pISER0 |= (1 << 3);
*pSTIR = (3 & 0x1FF);


This interrupt is **generated by software**, but handled exactly like a
hardware interrupt.


 4. Handler Mode Execution

When IRQ3 occurs:

* The processor switches automatically to **Handler mode**
* Handler mode is **always privileged**
* The ISR executes with full system access


void RTC_WKUP_IRQHandler(void)
{
    printf("In handler mode : ISR\n");
}


After ISR execution, the processor returns to **Thread mode (unprivileged)**.



CONTROL Register Summary

| Bit | Name  | Description                      |
| --- | ----- | -------------------------------- |
| 0   | nPRIV | 0 = Privileged, 1 = Unprivileged |
| 1   | SPSEL | Stack selection (not used here)  |

Key rule:

* Only **privileged Thread mode** can modify the CONTROL register
* Handler mode ignores CONTROL settings

---

Thread Mode vs Handler Mode

| Feature             | Thread Mode | Handler Mode |
| ------------------- | ----------- | ------------ |
| Executes main code  | Yes         | No           |
| Executes ISR        | No          | Yes          |
| Can be unprivileged | Yes         | No           |
| Privileged access   | Optional    | Always       |



ARM Thumb State (T-bit Explanation)

ARM Cortex-M processors support **only the Thumb instruction set**.

* The T-bit in xPSR indicates Thumb state
* On Cortex-M:

  * T-bit = 1 → Valid execution
  * T-bit = 0 → HardFault

ARM (32-bit ARM ISA) is **not supported** on Cortex-M3/M4.

If the T-bit is cleared (set to 0), the processor attempts to execute
an unsupported ARM instruction, resulting in a **HardFault exception**.

This behavior enforces Thumb-only execution on Cortex-M devices.



HardFault Handling


void HardFault_Handler(void)
{
    printf("Hard fault detected\n");
    while(1);
}


This handler captures invalid execution states such as:

* Illegal instruction execution
* Invalid T-bit state
* Unauthorized system access
